SecondLook eval framework — implementation reference

v12 (current) & v13 (planned)

End-to-end walkthrough of how each version processes a patient vignette from input to final ranked differential.

v12 — Current implementation
Multi-specialist + KB pipeline, fresh sampling
v13 — Planned dual-model architecture
Two foundation models + adversarial critique
v12 in one paragraph. A patient vignette enters as text. Symptoms and explicit excluded findings are parsed into structured form. A triage agent retrieves a knowledge-base candidate-disease shortlist. Eleven domain-specialist agents (all running on o3 reasoning:high in parallel) each see the case and a domain-tuned slice of the KB shortlist, and each emit 2–4 ranked diagnostic hypotheses with evidence mapping. An evidence-evaluator agent (o3 reasoning:high) deduplicates the hypotheses across specialists and scores each against KB diagnostic criteria where available. A synthesizer agent (o3 reasoning:high) reviews all hypotheses + criteria data and outputs a final top-10 ranking with LLM-assigned probability scores. A report-generator (gpt-4.1-mini) formats the patient-facing output. A deterministic family-expansion step appends up to 5 KB-linked sibling diseases at positions 11–15.

Input

A PatientCase object containing:

  • Demographics: age (string), sex (male / female / other)
  • Symptoms: array of MappedSymptom — each has an originalPhrase, a normalized medicalTerm, optional UMLS concept, severity, body part
  • Excluded findings: array of strings the source explicitly marked absent / denied / ruled out (used as negative evidence)
  • Patient hypothesis (optional): what the patient thinks they might have
  • Medical history: family history, past medical history, current medications, recent tests
  • Lab results (optional, real-user path only): structured LabResult[] from uploaded reports. No-op on eval cases.

For eval runs, the input is a Phenopacket2Prompt vignette converted to this shape. Lab fields are empty since the source vignettes don't include uploaded labs.

Sampling (eval path only)

For eval runs, the trio runner fetches a case via /api/admin/eval-case?count=N&mode=uniform. v12's sampler ignores any exclusion list and draws uniformly at random from all 9,587 Phenopacket2Prompt rows. This is the only behavior that differs from v11.

The 6-stage pipeline

1 Symptom Extraction & Triage gpt-4.1-mini + gpt-4.1-nano
~1–3s
Input PatientCase (with symptoms already parsed for eval; for real users, parse-symptoms runs first against the narrative text)
Work (a) Triage agent classifies body systems involved in the presentation (musculoskeletal / neurological / cardiovascular / immunological / etc.) and emits an acuity rating.
(b) Knowledge-base retrieval runs against the 9,263-disease KB. Multi-pass strategy: first pass filters by predicted body systems with a relevance threshold; second pass does an unfiltered KB sweep at a stricter threshold to catch triage misclassifications; third pass expands via KB-defined differential diagnoses of the top matches. Scoring blends disease-centric coverage (which of the disease's expected symptoms appear) with patient-coverage (what fraction of the patient's symptoms map to this disease).
(c) Triage ranks all 11 specialist types by case relevance. The ranking only controls display order; every specialist is consulted regardless.
Output TriageOutput: body systems, acuity, top KB candidate diseases with per-disease match score and matched symptoms, specialist ranking. KB retrievalLLM (nano)
▼
2 11 Specialist Agents (parallel) o3 reasoning:high × 11
~50–80s slowest
Input Each specialist receives the full PatientCase plus a domain-tuned slice of the triage KB candidates. The slice is computed by rerankCandidatesForSpecialty: the triage match score is multiplied by a domain-fit weight (explicit specialistType match = 1.0, body-system mapping = 0.45, fallback = 0.12).
Work Each specialist's prompt embeds (i) a specialty reference card with clinical frameworks, pattern-recognition heuristics, red flags, and common mimics drawn from established standards (ACR/EULAR, McDonald, Ghent, IUIS, etc.); (ii) the case demographics + symptoms + excluded findings; (iii) the KB candidate diseases with diagnostic criteria, prevalence, demographics, key symptoms by frequency tier. The general-internist is intentionally given no KB profiles — it serves as un-anchored counterweight.

Each agent emits 2–4 ranked diagnostic hypotheses with evidence mapping per hypothesis (supporting findings → patient symptoms, contradictory evidence, diagnostic criteria fit, typical presentation, clinical reasoning).

Reliability Each specialist call is wrapped in a 120s timeout. If 1–2 specialists time out or error, the pipeline continues with the survivors. If all 11 fail, the pipeline throws. Per-specialist outcomes are persisted (start time, completion time, hypothesis count, failure reason) to the testCase's pipelineProgressLog.
Output Array of AgentOutput — one per specialist that completed. Each contains 2–4 DiagnosisHypothesis objects. KB-anchoredLLM × 11 (o3:high)
▼
3 Evidence Evaluator o3 reasoning:high
~80–110s
Input All specialist outputs + the triage KB candidates + the full PatientCase.
Work (a) Deduplicate hypotheses across specialists (same disease proposed by multiple specialists merges into one entry; sourceAgent becomes comma-joined).
(b) Classify each hypothesis as KB-matched (its diagnosis name resolves to a KB disease profile via the tightened findDiseaseByName matcher, which requires ≥12-char name matches for substring fallback) or non-KB.
(c) For each hypothesis, evaluate against KB diagnostic criteria where available (criteria-grounded track) or via clinical reasoning quality where not (reasoning-evaluated track). Output structured criteria-fulfillment data: each formal criterion marked met / unmet with supporting evidence. Also emit evidenceQuality (strong / moderate / weak / insufficient), information gaps, contradictions, narrative strength assessment.
(d) Optionally add bonus subtype evaluations — variants the evaluator considers worth surfacing that weren't in the original specialist hypotheses.

A 30-second heartbeat progress event is emitted while the o3 call is in flight, keeping the SSE stream alive even when the underlying reasoning is silent.
Output EvaluationResult with deduplicated hypotheses, each enriched with diagnosticCriteria (totalCriteria / metCriteria / per-criterion details), evaluationType, knowledgeBaseMatch, evidenceQuality enum, contradictions array, strength assessment. KB criteriaLLM (o3:high)
▼
4 Synthesizer (rank decision) o3 reasoning:high
~30–60s
Input All evaluated hypotheses with criteria data + specialist outputs + the full PatientCase.
Work Senior-diagnostician system prompt. The LLM reviews all hypotheses and the criteria-fulfillment data, applies its own clinical judgment + Bayesian reasoning + demographic fit, and produces a top-10 ranking with a probability score per diagnosis (0–100), a reasoning string per diagnosis, a consensus level for the differential (strong / moderate / weak / divergent), critical information gaps, common diagnoses explicitly excluded with reasons, and differential clusters (groups of phenotypically indistinguishable siblings with their distinguishing tests).

The synth's probabilityScore becomes the rank key. It is stored in both confidenceScore and evidenceScore on each hypothesis. The mechanical formula is computed in parallel and persisted as evidenceScoreRaw / evidenceScoreBreakdown for audit and as the LLM-vs-formula divergence signal — but it does not change the ranking.

If all top-5 scores fall below 40 OR specialist consensus is weak/divergent OR top-diagnosis reliability is rated low, an escalation context is injected into the report generator's prompt recommending broader investigative pathways (WES/WGS, geneticist referral, undiagnosed disease programs).

Heartbeat events fire every 30s during the call.
Output Top-10 ranked DiagnosisHypothesis array sorted by evidenceScore desc, plus a SynthesisOutput record containing consensus level, escalation context, differential clusters, excluded common diagnoses. LLM clinical judgment (o3:high)
▼
5 Report Generator gpt-4.1-mini
~20–35s
Input Synthesis output (ranked hypotheses + clinical narrative + clusters + escalation context if any).
Work Formats the patient-facing report. Output structure: top-10 ranked diagnoses (preserving synth's order), per-diagnosis recommended testing, next steps (immediate actions / specialist referrals / follow-up timing / red flags), data gaps, recommended labs section, overall assessment.

When the escalation context is injected, the report acknowledges low diagnostic certainty and recommends broader pathways.
Output ReportResult with patient-facing report data plus the same top-10 hypotheses ready for family expansion. LLM formatting (gpt-4.1-mini)
▼
6 Family Expansion (deterministic) no LLM
<1s
Input The top-10 ranked diagnoses from the report stage.
Work For each of the top-10 diagnoses, look up the disease in the KB via findDiseaseByName. If it resolves to a KB profile that has a non-empty differentialDiagnoses field (KB-defined sibling diseases), append up to 3 of those siblings to the output, capped at 5 total expansions across the top 10. Skip variants whose normalized name is already present in the top 10 or among already-added expansions.

Expansions are tagged sourceAgent: 'family-expansion' and expansionSource: 'family'. Scores are set to 0 (silent zero — the user sees the expansion as a related variant but not as a ranked competitor to the LLM-ranked top 10).
Output Up to 5 additional DiagnosisHypothesis entries for positions 11–15 with score=0 and a parentDiagnosis back-reference. KB lookupdeterministic

Final output

The pipeline assembles an AnalysisResult:

{ differentialDiagnoses: DiagnosisHypothesis[], // up to 15 entries: top-10 LLM-ranked + up to 5 family expansions differentialClusters: DifferentialCluster[], // phenotypic-sibling groups with distinguishing tests familyEnrichments: FamilyEnrichment[], // optional KB-grounded family-of-disease enrichment excludedCommonDiagnoses: ExcludedCommonDiagnosis[], // common conditions explicitly ruled out, with reasons dataGaps: string[], // missing information that would clarify the differential recommendedTesting: string[], // labs / imaging / genetic tests to order nextSteps: { // immediate actions, specialist referrals, follow-up timing immediateActions: string[], specialistReferrals: string[], followUpTiming: string, redFlags: string[] }, overallAssessment: string, // synth's honest summary of the diagnostic picture pipelineMetadata: { stages: StageResult[], // per-stage duration, tokens, model — including any specialist-failed entries budgetSummary: { estimatedCostUsd: number, ... }, pipelineVersion: "2.1.0" } }

Each DiagnosisHypothesis carries: diagnosis name, ICD-10 / OMIM / Orphanet IDs, confidenceScore = synth's LLM probability = the rank key, evidenceScore identical to confidenceScore, evidenceScoreRaw and evidenceScoreBreakdown from the mechanical formula (audit data only), rareDisease flag, prevalence string, supporting and contradictory evidence arrays, clinical reasoning, typical presentation, specialist required, full diagnosticCriteria object (criteriaName / totalCriteria / metCriteria / per-criterion details / fulfillmentPercentage), sourceAgent (or sourceAgents array if multiple specialists proposed it), evaluationType (criteria-grounded / reasoning-evaluated), knowledgeBaseMatch flag, scoringVersion tag, parentDiagnosis back-reference if a family-expansion entry.

Eval-specific grading flow

For eval-mode runs, after the pipeline returns its AnalysisResult the trio runner sends the top-10 diagnoses plus the ground-truth diagnosis to /api/admin/grade-test. Grading runs in two passes:

  • Pass 1 (deterministic): tier-match against ground-truth by name normalization, ICD-10, and Orphanet ID. Determines the tier (exact-top1 / exact-top3 / exact-top5 / variant-top3 / variant-top5 / family-top3 / family-top5 / organ-system / complete-miss) which constrains the score range.
  • Pass 2 (LLM, Claude Sonnet): scores reasoning quality within the tier's allowed range. Awards 0–100, qualitative grade A+ through F, plus strengths / weaknesses / missed findings / false leads / partial-credit reason.

Key knowledge-base interactions

  • Triage retrieval: multi-pass scoring across ~9,263 KB diseases with embeddings + symptom-tier matching + demographic fit.
  • Per-specialist rerank: each specialist's KB shortlist is filtered + ranked by domain-fit weight against the specialty mapping.
  • Evidence evaluator: criteria-grounded evaluation requires resolving each hypothesis to a KB profile via findDiseaseByName (tightened matcher: ≥12-char min for substring fallback to prevent the Ciliopathy bug class).
  • Family expansion: deterministic lookup of each top-10 diagnosis's KB-defined sibling diseases.
  • Mechanical formula (audit only): per-component score for each hypothesis based on criteriaFulfillmentRatio, symptomMatchScore, specialistAgreement, contradiction penalty, excluded-finding penalty.

The 5-stage pipeline

1 Symptom Extraction gpt-4.1-mini
~1–2s
Input PatientCase (with symptoms pre-parsed for eval; for real users, parse-symptoms runs first).
Work Identical to v12 stage 1's parsing leg. No KB retrieval at this stage in v13 (KB is consulted post-generation, not pre-generation).
Output Structured PatientCase with mapped symptoms and excluded findings. LLM (parsing)
▼
2 Dual-Model Generation (parallel) opus-4-7 + o3 reasoning:high
~30–50s
Input Both generators receive the same prompt: the full structured PatientCase (demographics, symptoms, excluded findings, medical history, optional labs). No KB candidate shortlist. Each model generates from its own training-weight medical knowledge unconstrained.
Work Two independent calls run in parallel. Each model is instructed to produce a ranked top-10 differential with a one-sentence clinical reasoning per diagnosis, ranked by probability descending. Output structure mirrors the Phenopacket2Prompt official benchmark protocol.

Each call is wrapped in a per-model timeout (estimated 90s ceiling; opus-4-7 typically completes faster than o3:high). If one of the two errors or times out, the pipeline still continues with the survivor.
Claude opus-4-7

Broad medical training; measured ranking-quality edge on long-tail rare diseases (54% Top-3 vs SL's 25% in v11). Tends to surface the obvious-correct answer near the top when it has it.

OpenAI o3 reasoning:high

Same model that powers v12's specialists, evaluator, and synthesizer. Strong reasoning depth; consistent single-shot performance (~40% Top-1 across cohorts). Different training distribution than opus.

Output Two RankedDifferential arrays (one per generator), each with 10 diagnoses + reasoning + probability score. LLM × 2 generators
▼
3 KB Augmentation (deterministic) no LLM
<2s
Input Union of unique diagnoses across both generators' top-10 lists (expected: 12–18 unique entries after dedupe across the two models).
Work For each unique diagnosis, look up the KB via findDiseaseByName. If a KB profile resolves, attach:
  • Formal diagnostic criteria (criterion name, criteria array, minimum-for-diagnosis statement)
  • Red flags
  • Recommended confirmatory testing (laboratory / imaging / genetic / other from the KB's keyFindings structure)
  • Prevalence classification (ultra-rare / rare / uncommon / common)
  • KB-defined family-variant siblings (from differentialDiagnoses field)
  • Which generator(s) proposed it (modelsThatProposed: 'opus' | 'o3' or both)
Diagnoses without a KB match are kept with empty augmentation. The KB does not filter or constrain candidates — it only attaches citation data to what the generators already produced.
Output Augmented CandidateDiagnosis array with full KB-grounded clinical-citation metadata per entry. KB lookupdeterministic
▼
4 Adversarial Critique & Reconciliation Claude opus-4-7
~10–20s
Input The full PatientCase + both generators' top-10 lists side-by-side + the augmented KB data per unique diagnosis.
Work The critic system prompt frames the task as:
  • Identify missing candidates: diagnoses that the vignette pattern strongly suggests but neither generator surfaced. Use the KB's family-variant siblings of generator candidates as suggestion seeds.
  • Identify ranking errors: candidates where the generators disagreed on rank meaningfully, or where one generator placed a downstream-condition above its cause (e.g. Secondary HPT above ADTKD-1), or where a vague umbrella diagnosis outranks a specific variant.
  • Identify near-duplicates and clusters: phenotypic-sibling diagnoses that should be deduplicated or grouped into a "family cluster" (e.g. multiple DEE subtypes, multiple OI types).
  • Produce a reconciled top-10 ranking with explicit per-entry deltas: "kept opus #1", "promoted o3 #4 → #2 because…", "dropped opus #6 as duplicate of #3", "added new #7: X (suggested by KB family variant of opus #2)".
Critic role uses Claude opus-4-7 specifically. Empirically opus has shown stronger ranking quality than o3 on long-tail rare diseases (v11 cohort: 54% Top-3 vs SL's 25%) — putting it in the critic seat leverages that ranking-judgment edge to reconcile the two generator outputs. No reasoning-tokens stage means typical latency is meaningfully shorter than an o3:high call.
Output Final ranked top-10 DiagnosisHypothesis array with per-entry critic rationale and a delta-explanation log. Probability scores are the critic's clinical-judgment scores (0–100). LLM critique (claude-opus-4-7)
▼

~15–25s
Work (a) Mechanical formula runs over the critic's top-10 and persists per-component scores (criteriaFulfillmentRatio from the augmented KB data, symptomMatchScore from KB symptom overlap, modelAgreementScore based on whether both generators or only one proposed each diagnosis, contradictionPenalty, excludedFindingPenalty). Audit data only — does not change the critic's ranking.
(b) Report generator formats the patient-facing structure (ranked diagnoses with criteria documentation, recommended testing pulled from KB, next steps, red flags). Same output schema as v12 stage 5.

Final output

Identical AnalysisResult schema as v12 so downstream consumers (the grading pipeline, the user-facing UI, the testing-shared display, the matched-trio comparison) don't need to change. v13 outputs 10 diagnoses (positions 1–10); no family expansion at positions 11–15 is needed because the dual-generator panel + KB augmentation already broadens the candidate pool.

Each DiagnosisHypothesis in v13 carries the same fields as v12 plus three v13-specific additions: modelsThatProposed: ('opus' | 'o3')[], criticDelta: string (the critic's per-entry rationale), and finalRank: number.

Architectural rationale

What changed from v12 (philosophically)Why
11 same-model specialists → 2 different foundation models 11 specialists in v12 are all the same base model (o3) with different prompts. Diversity comes from prompt variation, not training distribution. v13 uses two genuinely different models (opus-4-7 + o3) to get real distribution diversity. Empirically, Claude opus and OpenAI o3 have measured different strengths on different sub-populations of rare diseases.
KB as candidate-filter → KB as post-hoc citation v12's KB-anchored specialist shortlists demonstrated specialist herding on KB-adjacent wrong families (the OI-IX failure: 3 specialists converged on Bruck, 6 on Hypophosphatasia, none on Osteogenesis Imperfecta). v13 lets the foundation models generate from full medical knowledge unconstrained, then uses KB to document and validate what was generated.
Single synth-as-judge → adversarial critic (Claude opus-4-7) v12's synthesizer takes one perspective and ranks. v13's critic explicitly looks for what the generators missed and where they ranked badly. The structure of "two independent generations + one explicit reconciler" forces the critic to address disagreement rather than smooth over it. The critic role is filled by opus-4-7 because empirical measurements showed opus has stronger ranking quality than o3 on long-tail rare diseases — placing it in the judgment seat (rather than the generation seat) leverages that edge.
Mechanical formula as audit, mechanical formula as audit v13 keeps the v10/v11/v12 decision that LLM judgment, not a formula, ranks. The mechanical formula's diagnostic value as an audit signal is preserved.

Provider boundary

v13 deliberately uses both OpenAI and Anthropic in the analysis path. This crosses the AI Provider Separation rule documented in CLAUDE.md, which previously kept analysis on OpenAI-only and testing on Anthropic-only as quota isolation.

The per-case provider split: 2 Anthropic calls (opus generator + opus critic) and 2 OpenAI calls (o3 generator + gpt-4.1-mini report). Anthropic load is meaningful and warrants monitoring against the grading-flow's separate Sonnet usage on the testing framework side. The tradeoff: real long-tail accuracy gain from Claude opus's measured advantage in both generation breadth and ranking judgment vs. coupling analysis quota to Anthropic. For published-dataset eval where the headline metric is deterministic OMIM/name matching, the cross-provider objectivity concern is small.

Implementation plan

Four small modules land sequentially, each behind the feature flag so v12 stays intact:

  • 1. lib/agents/dual-generator.ts — fires opus and o3 in parallel, normalizes outputs to the existing DiagnosisHypothesis shape, marks modelsThatProposed.
  • 2. lib/pipeline/kb-augmentation.ts — pure function, no LLM. Walks each unique diagnosis and attaches KB metadata. Reuses the tightened findDiseaseByName.
  • 3. lib/agents/critic-agent.ts — single Claude opus-4-7 call (via the existing callAnthropic helper) with structured JSON output (final ranking + dropped + added + downstream flags + clusters). No reasoning-effort knob (opus has no extended-reasoning mode); typical latency 10–20s without heartbeats needed.
  • 4. lib/pipeline/orchestrator.ts — top-level branch reads evalEngine. Classic path (existing) or dual path (new modules). Engine choice persisted on test cases (evalEngine: 'classic' | 'dual') so the matched-trio table can split that dimension the way it already splits sampling mode.

Mechanical scoring + report stages are reused from v12 as-is.
