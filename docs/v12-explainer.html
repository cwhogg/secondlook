v11 / v12 — Pipeline & Analysis Plan

Two consecutive eval versions explained side-by-side. Pipeline architecture, what changed at each step, what we're measuring, what we'll decide.

v11 — Ranking parity revert
Drops two v7 post-processors
v12 — Fresh-pool sampling
Pipeline unchanged from v11
TL;DR — v11: Same multi-agent pipeline as v10. Three things removed from the post-synthesis path so the rank order matches v5 exactly: the downstream-condition penalty (halved the score of any diagnosis listed as a downstream consequence of another), the family-expansion scoring (positions 11–15 used to inherit half the parent's score; now back to silent zeros), and the downstreamOf field from the evidence-evaluator's structured-output schema. Mechanical scoring still runs and is persisted as audit data, but doesn't drive ranking. Tested whether the v10→v11 gap to v5's 54% Top-1 was these processors or just cohort variance.

What v11 removed (and why)

v7 introduced a deterministic mechanical scoring layer that ran after synth's LLM ranking. v10 already restored the LLM probabilityScore as the rank key. v11 removes the last three v7 additions that were still in the path:

REMOVED
applyDownstreamPenalty()

Halved evidenceScore for any diagnosis the evidence-evaluator listed as a downstream consequence of another diagnosis in the same differential. Designed to fix the ADTKD-1 failure pattern (Secondary HPT outranking the underlying ADTKD). Specific bug fix; v5 didn't have it.

REMOVED
applyFamilyExpansionScoring()

Gave positions 11–15 (KB-linked family variants appended after synthesis) a score of parent.evidenceScore × 0.5. v5 had these at silent zero. v11 reverts to zero so the UI tier ("Weak fit") matches v5 expectations.

REMOVED
downstreamOf field on evaluator schema

The evidence-evaluator's structured-output schema previously required the LLM to emit, for each hypothesis, a downstreamOf: string[] array naming other diagnoses in the differential that this one is a complication of. Used by applyDownstreamPenalty. Removing the field gives the evaluator a prompt identical to v5's, eliminating any subtle effect on the LLM's reasoning from having to produce that field.

KEPT (audit only)
computeMechanicalEvidenceScore() + breakdown persistence

The mechanical formula still runs for every hypothesis and persists per-component data (evidenceScoreRaw, evidenceScoreBreakdown, sourceAgents, scoringVersion). Useful as audit data and as the "LLM vs mechanical formula divergence" diagnostic. Does not feed into the rank key.

Six stages. KB lookups at retrieval (stage 1), per-specialist KB shortlists (stage 2), and the deterministic family expansion (stage 6). Synthesizer's LLM probability is the rank key.

How to read the v11 numbers

  • OAI dropped from 43% (v10) to 21% (v11) Top-1 on an unchanged model — that's a cohort-difficulty signal of about 22 pts. The v11 cohort was meaningfully harder for everyone.
  • SL dropped from 40% (v10) to 21% (v11) Top-1 — 19 pts drop, slightly less than OAI's 22 pts. Adjusted for cohort drag, SL improved ~3 pts relative to OAI from the architectural revert. Within noise.
  • Claude opus has a clear ranking-quality edge: 54% Top-3 vs SL's 25%. Claude finds the right answer in its top three twice as often. SL's hits are spread across rank 6–10 (Top-10 = 50%, Top-5 = 29%). Specialist herding pattern visible at the cohort level.
  • The architectural revert didn't recover v5's 54% Top-1. Two possibilities: either v5 was an unrepresentative draw, or the v11 cohort had a much harder composition than v5's did. v12 tests this by removing the sampler depletion bias.

The eval-case sampler had been excluding ppkt_ids with already-completed graded trios. Early batches drew freely from the corpus-concentrated diseases; by later batches those had all been consumed. The v5-vs-v11 measurement was partially measuring different sub-populations of the corpus, not the same architecture on the same data. This finding is what motivates v12.

TL;DR — v12: The v11 diagnosis pipeline unchanged. The only change is a single line in the eval-case sampler: it no longer excludes ppkt_ids that already have completed trios. Each batch now draws fresh from the full 9,587-case Phenopacket2Prompt corpus, matching the methodology published benchmarks used. The goal is one clean apples-to-apples measurement of the SL pipeline on a sampling-stable cohort.

What v12 changes (just one line of code)

v11 sampler

Excluded ppkt_ids with already-completed graded trios

↓ pool shrinks every batch

Effect: the corpus-concentrated top-15 diseases (DEE4×462, NF1×405, KBG×333…) got consumed by early batches. Later batches drew disproportionately from the long tail, where SL's KB has weaker coverage. Apparent accuracy declined over time even though no architectural code changed.

v12 sampler

Draws from the full 9,587-row corpus, no exclusion

→ pool is the same every batch

Effect: cohort composition is statistically stable across batches. Measurements are directly comparable to published Phenopacket2Prompt benchmarks (Exomiser 35.5%, o1-preview 23.6%, GPT-4o ~20%), which also sampled without depletion.

One change in app/api/admin/eval-case/route.ts: the exclude query parameter is now ignored. Pipeline is identical to v11.

The v12 analysis plan

Step 1 — run a batch (target N ≥ 30 uniform)

Trio runner draws fresh from the full pool. Expected composition mirrors the corpus distribution: ~28% top-15 cases, ~72% long-tail.

Step 2 — three measurements

  • Headline Top-1 / Top-3 / Top-5 / Top-10 across SL, OpenAI o3, Claude opus-4-7. Same case denominator across all three (matched-trio comparison).
  • Comparison to published baselines. v12 methodology now matches Exomiser / o1-preview / GPT-4o's measurement protocol.
  • Stratified by corpus frequency — split graded cases into "top-15 corpus disease" vs "long tail" and compute Top-1 on each. Reveals where the architecture wins and where it doesn't.

Step 3 — decision branch for v13

SL ≥ baselines by ≥10 pts v13 = optimize for cost
Pipeline is genuinely strong on representative data. v13 explores whether we can keep the win while cutting per-case wall time (~120s) and cost (~$1.50). Likely: replace redundant specialist role-plays with shared embeddings + critique pass.
SL ≈ baselines
(within 5 pts either way) v13 = dual-model architecture
The 11-specialty mechanism is theatre at the scale we're using it. v13 ships the queued dual-model + adversarial critique design (opus-4-7 + o3 generators, KB as post-hoc citation only). Behind feature flag; specialty agents kept in tree for revertability.
SL < baselines by ≥5 pts urgent v13 = redesign
Architecture is actively hurting on representative data. Same dual-model direction, plus deeper investigation of KB-anchored failure modes. KB curation may need triage before further architectural work.

Step 4 — disaggregate the why

For cases SL missed but at least one baseline hit, walk the persisted pipeline trail (pipelineProgressLog, per-specialist hypotheses, evidence-evaluator output) and classify the failure mode:

  • Specialist herding — all 11 converged on a KB-adjacent wrong family (OI-IX pattern)
  • KB variant absence — specific gene-level variant isn't in the KB (OPA12 pattern)
  • Synth ranking bias — correct answer was in the candidate pool but mis-ranked (Loeys-Dietz pattern)
  • Routing failure — vignette type pushed specialists toward wrong domain (Netherton pattern)
  • Grader miss — pipeline got it right; grader nomenclature failed (Complex IV ≡ Cytochrome c Oxidase pattern)

The mix of failure modes determines whether v13 should change agent architecture, KB, scoring, or all three.

What v12 deliberately doesn't try to do

  • Doesn't change the architecture. Specialty agents, KB-grounded retrieval, multi-pass scoring, synth-as-ranker — all unchanged from v11.
  • Doesn't try to win on the long tail. If v12 confirms SL is tied or losing there, that's a v13 problem.
  • Doesn't try to optimize cost or latency. Same ~$1.50/case and ~120s wall time as v11.
  • Doesn't reset previously-saved test cases. v5 / v10 / v11 historical data stays in KV and remains queryable; v12 results sit in a separate cohort block in the comparison table.
